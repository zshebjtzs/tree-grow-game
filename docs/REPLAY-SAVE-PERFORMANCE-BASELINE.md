# TreeGrow 大型存档性能基线（F0）

## 范围

本次审查基于 main 分支提交 `e48959cbe7118a72d7d9740f70af8e0824c3e61e`。
本文件记录静态代码审查发现与可复现的基准测试入口；未把未经实际运行的耗时或压缩率写成测量结果。

## 当前数据流

1. 游戏保存：`getGameBlob()` 将完整存档对象以带缩进的 JSON 序列化，再创建 Blob。
2. 正式读档：`loadGame()` 调用 `file.text()`、`JSON.parse()`，然后执行正式存档验证。
3. 回放导入：`importReplayFile()` 先按文件字节数拒绝超过 20 MiB 的文件，再执行 `file.text()`、`JSON.parse()` 和 `ReplaySaveValidator.validate()`。
4. 回放验证：从地图种子重建地图，验证当前局面、初始快照、每一步快照和行动链路，最后创建隔离的回放会话。

## 已确认的性能热点

### 1. 快照链验证重复工作

原实现先验证初始快照；每个行动又分别验证 before/after，然后再次对 before/after 调用 `GameState.fromJSON()`。因此每个行动的两份快照都重复构造游戏状态，且 before 快照实际上已经等于前一步已验证的 after 快照。

F0 优化：初始快照只验证一次；每步只验证新的 after 快照，并将其已验证的 GameState 传递给下一步行动。before 仍进行完整结构相等性比较，行动方、回合、节点编号、路径和 skip 规则仍逐步验证。

### 2. 快照相等性比较产生大型临时字符串

原实现递归构造排序后的完整 JSON 字符串，再比较两个字符串。这会为大型快照分配额外字符串，并对所有对象键排序。

F0 优化：改为递归结构比较，不构造完整序列化副本；数组顺序保持敏感，对象键顺序不敏感。

### 3. 验证结果重复复制整份存档

原实现深拷贝整个原始存档，再单独深拷贝棋谱；随后 `ReplaySession` 再次将棋谱解析为独立历史。回放入口只需要经过验证的棋谱和少量元数据。

F0 优化：验证结果只浅拷贝顶层对象；`MatchHistory.fromJSON()` 已经生成与原始输入隔离的历史实例，验证器将该实例直接交给 `ReplaySession`，避免再次执行整份棋谱的 toJSON/fromJSON 深拷贝。地图种子和游戏局面也不再被额外深拷贝。正式回放状态仍由独立 `ReplaySession` 管理。

### 4. 存档序列化存在明显可压缩空间

原实现使用 `JSON.stringify(data, null, 2)`，把大量空格和换行写入文件。长棋谱的前后快照还具有大量重复字段和值，适合通用 gzip 压缩。

F2 优化：新存档使用紧凑 JSON，并在运行环境支持 Compression Streams API 且压缩确实减小文件时使用 gzip。文件增加 `TGSV\x01\n` 标识头；旧版纯 JSON 存档继续可读。存档内部 schemaVersion 和 MatchHistory 数据模型不变。

## 自动恢复存储的边界

正式对局的最近对局自动恢复数据另存于 `localStorage`，由 `persistLastMatch()` 写入完整 JSON。它不是回放文件导入链路，因此不会受到原 20 MiB 拒绝条件影响；本次也不把它改为压缩字符串或 IndexedDB，以免引入异步写入竞态、浏览器配额和迁移问题。该路径仍可能受浏览器本地存储配额限制，后续若玩家反馈自动恢复数据写入失败，应单独评估存储后端，而不是重新引入文件大小上限。

## 复杂度与预期

- 快照链比较仍需检查快照字段，时间复杂度与被比较数据规模线性相关，但避免了两份完整临时字符串。
- 每个行动只对新 after 快照执行一次完整地图/节点/游戏状态验证；不再重新验证已确认的 before 快照。
- gzip 压缩率依赖真实对局内容；重复快照字段通常有较高可压缩性，但实际收益应以基准脚本输出为准。
- 压缩/解压仍会消耗 CPU 和内存；本阶段不承诺无限文件大小，也不引入新的固定大小上限。

## 可复现基准

运行：

`npm run benchmark:replay`

脚本生成 100、1,000、5,000、10,000 步的合法 skip-only 长时间线，输出 JSON 字节数、最终存档字节数、压缩比、序列化耗时、完整验证耗时和编码耗时。该基准用于比较算法路径和验证吞吐，不代表复杂战斗局面的最大负载；真实对局仍需在后续 F3/F5 阶段补充端到端设备测量。

## 本次边界

不改变前后快照模型、不引入增量棋谱或检查点、不修改悔棋规则、不削减任何存档验证规则。Worker 化导入和虚拟列表属于后续 F3/F4。
