# Stage F0 — AI 架构审查与性能基线

状态：F0 技术审查完成；运行时基准由 CI 工作流持续采集。本文描述审查时 `main` 的真实实现，不代表后续阶段已实现。

## 2. 当前实现事实

### 决策链

1. 主线程的 `triggerAITurn()` 序列化当前 `GameState`，并将邻接表、区域中心、难度、阵营和基地 ID 发送给 Worker。
2. Worker 校验请求字段，创建 `AIController` 并调用 `getBestMove()`。
3. Controller 从 JSON 恢复状态，生成合法候选行动。
4. 每个候选行动调用 `_scoreMove()`；其中会执行路径距离计算、完整状态模拟和战斗结算。
5. 简单难度从评分前 4 个行动中随机选择；普通难度对前 8 个行动加权随机；困难难度先取评分前 7 个候选，再进行 AI 行动与对手回应的两层搜索。
6. Worker 返回行动；主线程再次验证行动合法性，再交给正式游戏流程执行。

### 当前实现边界

- 难度仅支持 `easy`、`medium`、`hard`，专家难度尚不存在。
- 困难搜索宽度固定为 7，且不是通用的 Minimax/Alpha-Beta 搜索引擎。
- `_simulateMove()` 每次都通过 `toJSON()/fromJSON()` 复制完整状态，再运行规则校验、节点创建、战斗和回合转换。
- `_distanceToBase()` 对每棵树的每个存活节点分别执行 BFS；候选评分中会多次重复计算。
- `_generateMoves()` 对候选目标逐个调用 `RuleEngine.canGrow()`；该方法会重新构造占用集合并执行路径搜索。
- 当前没有置换表、局面哈希、增量评估、搜索节点计数或正式性能基准。
- Worker 当前在决策完成后使用 300ms 定时器再返回结果。这是人为延迟，不是计算耗时；F0 将其移除。
- Worker 采用同步计算。消息事件不能在同步搜索中途执行，因此不能依赖发送新消息来取消正在运行的搜索。后续需要通过预算检查或终止/重建 Worker 实现取消。

## 3. 当前测试覆盖

`js/ai/AIController.test.js` 当前覆盖：

- 从快照恢复并返回合法行动。
- 根节点首次生长可使用非直接邻接目标。
- 所有现有难度识别立即获胜行动。
- 朝敌方基地推进的路径距离评分。
- 无效难度与无效阵营拒绝。
- 三档行动均可通过 RuleEngine 复核。
- 堡垒作为唯一攻击目标时拒绝行动。
- 所有己方生长父节点被冻结时返回无行动。
- 战斗模拟正确保留防守方冻结状态。

目前没有独立的 Worker 消息协议测试，也没有固定局面战术回归集。现有测试没有覆盖专家难度（尚未实现）、深层搜索、搜索超时、置换表正确性或性能回归。

## 4. 已识别的主要性能热点

按预期收益与风险排序：

1. **重复 BFS**：候选评分反复计算双方到基地的距离；同一局面内地图拓扑不变，可以考虑预计算反向距离场，并按占用状态做精确修正。
2. **重复占用集合与合法性路径检查**：每个候选目标重新扫描节点和构建 Set。可在单个局面内构建共享索引，但必须保持 RuleEngine 的占用与路径语义一致。
3. **完整状态 JSON 深拷贝**：搜索每个分支都复制全量节点数据。后续应评估紧凑搜索状态、可逆 make/unmake 或结构共享；必须先证明战斗、冻结、回合切换和父子连接语义完全一致。
4. **重复战斗/局面评估**：可通过缓存或增量特征降低重复工作，但缓存键必须包含影响规则结果的完整状态信息。
5. **搜索效率**：当前困难模式没有 Alpha-Beta、迭代加深和置换表。后续应先保证行动排序与搜索值定义正确，再逐步引入剪枝。

不应以缩小候选宽度或降低搜索深度作为首选优化。优化前后需要在相同搜索范围/深度下对照节点数、耗时和决策结果。

## 5. 建议目标架构（F0 设计产物，后续阶段实施）

| 模块 | 单一职责 |
|---|---|
| `MoveGenerator` | 基于统一规则生成候选行动 |
| `TacticalAnalyzer` | 识别立即胜利、紧急防守、根威胁、关键分叉与冻结机会 |
| `PositionEvaluator` | 统一计算战术、树结构、空间、防守和长期布局价值 |
| `SearchEngine` | 搜索、行动排序、剪枝、缓存、预算与迭代加深 |
| `DifficultyProfiles` | 纯配置定义风格、评估偏好与搜索预算 |
| `DecisionExplainer` | 从实际命中的决策特征生成解释摘要 |
| `AIController` | 编排决策流程并保持外部接口稳定 |
| `AIWorker` | 后台执行、请求校验、结果回传和异常处理 |

搜索模拟必须与正式规则同源，不能自行复制一套不完整的战斗规则。主线程对 Worker 返回的行动继续进行二次合法性验证。

## 6. 性能基准方法

新增 `npm run benchmark:ai`，在固定的 50 区域合成拓扑与固定局面上测量 easy/medium/hard：

- 预热后执行多轮决策。
- 记录每档样本数、p50、p95、平均值和最大值。
- 输出 Node.js 版本、平台和架构，便于比较运行环境。
- 基准结果用于观察趋势，不设置脆弱的 CI 毫秒阈值；共享 CI 主机负载不稳定，不能将单次耗时作为正确性门槛。

该基准测量当前同步决策函数耗时，不等价于真实浏览器 Worker 端到端延迟，也不代表真实随机地图所有局面的最坏情况。F1/F3 还应增加多种固定局面（低/中/高分支、攻击密集、节点数量较多）并在目标浏览器/设备上复测。

## 7. F0 后续阶段的工程约束

- 不人为模拟 AI 思考时间；计算完成后立即回传。
- 不允许主线程执行重型搜索。
- 先通过算法减少重复计算与无效分支，再考虑搜索预算内提前终止。
- 任何预算中止都必须返回最近一次完整、合法的搜索结果；不能返回半完成节点的临时值。
- 搜索预算是响应保护，不是主动降低棋力的常规手段。
- 所有难度使用相同规则；动态难度不在 Stage F 范围内。
- 所有优化都要做规则正确性回归、相同搜索范围下的结果对照和性能基准。

## 8. 当前基准数据状态

代码结构基线已确认。具体毫秒数应以 `benchmark:ai` 在 CI 和目标设备的实际输出为准；本次远程仓库审查没有本地 Node.js 执行环境，因此不伪造运行时数字。CI 基准输出用于建立首个可重复的自动化采样，目标设备实测仍是性能验收依据。
